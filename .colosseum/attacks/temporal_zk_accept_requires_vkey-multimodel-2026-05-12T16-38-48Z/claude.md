VERDICT: BREAKS

The temporal property does not capture the intent. It witnesses a vkey state that may be irrelevant to whether the proof was actually verified, and it leaves several composition paths to `Accepted` unguarded. Six attacks below, four serious or critical.

---

## 1. Mock mode + empty proof yields `Accepted` with the property vacuously satisfied

- **Category**: Under-specification
- **Severity**: critical
- **Scenario**: Execute the trace `init` → `enable_mock` → `verify_any(msg)` where `msg = { msg_hash: VALID_MSG_HASH, attestation: { variant: Zk, user_data: VALID_MSG_HASH, compose_hash: VALID_COMPOSE_HASH, proof: EMPTY_PROOF, ... } }`. After `init`, `config.zkdcap_vkey == VALID_VKEY` and `registered_vkeys` contains it. The else-if at line 245 only rejects `proof_bytes == ""` when `accept_all` is false; with mock on, control falls through to the final `else` at line 255 and `last_result' = Accepted`. The temporal property's RHS at lines 422-423 evaluates `config.zkdcap_vkey != "" and registered_vkeys.contains(...)` — both true — so the property holds while a wholly empty proof has been accepted.
- **Why it succeeds**: Intent at `CLAUDE.md` line 13-14 specifies "Mock mode: ... skips ZK verification" as a *substitution* of attestor types in the off-chain flow. The on-chain temporal property is the only artifact claiming to gate `Accepted` to "the vkey is set and registered"; it provides zero information about whether mock mode has subverted that gate. The property name promises a precondition for safe acceptance; in mock mode the precondition is structurally orthogonal to safety.
- **Suggested defense**: Either (a) make `temporal_zk_accept_requires_vkey` conjoin with `not(zk_module.accept_all)` so mock-mode acceptances are explicitly outside the property's scope, or (b) strengthen the antecedent to bind `next(last_input.attestation.proof.proof_bytes) != "" or not(zk_module.accept_all)` and add a sibling property `temporal_mock_mode_disabled_in_production`. Note this overlaps with Round-1 Finding 1 but the categorisation here is `Under-specification` not `Coverage gap`: the spec admits the bad behavior; it isn't merely silent on it.

## 2. The temporal property cannot distinguish `Accepted -> Accepted` from a real new acceptance

- **Category**: Triviality (transition-encoding bug)
- **Severity**: serious
- **Scenario**: Trace: a successful `verify_zk` produces `last_result = Accepted`. Then `enable_mock` runs — which writes `last_result' = last_result`, i.e. preserves `Accepted`. Then `clear_vkey` runs — writing `last_result' = last_result` again and setting `config.zkdcap_vkey = ""`. Then a second `verify_zk` runs on a Zk msg, which now hits the `config.zkdcap_vkey == ""` branch at line 225 and sets `last_result' = SkippedNoVKey`, NOT `Accepted`. So the property's antecedent at line 419 — `last_result != Accepted and next(last_result) == Accepted` — is never re-armed for the *next-after-that* genuine `verify_zk` either, because the only way to re-arm is to first leave `Accepted`. Reachable, but the property cannot fire on consecutive acceptances. In a longer trace where `verify_zk` re-accepts directly (e.g. `last_result` is currently `RejectedZkProofInvalid` then `verify_zk` succeeds), the property does fire — but the comment at lines 414-417 explicitly justifies excluding stutter steps without acknowledging that this excludes *legitimate consecutive accepts* too. There is no scenario the spec gives where `Accepted -> Accepted` is reached by a real `verify_zk` (because `last_result` is overwritten by the action, not the prior state), so the gap is not exploitable in this exact spec — but the property's logic is brittle to any refactor.
- **Why it succeeds**: Comment at lines 414-417 reasons only about `clear_vkey` stutter, missing the broader class of `last_result == Accepted and next(last_result) == Accepted` transitions. The `verify_zk` action *does* write `last_result' = Accepted` in its success branch (line 258), unconditionally overwriting the prior value. If two successful `verify_zk` calls run consecutively, the second is invisible to this property. This is precisely the case the property claims to monitor.
- **Suggested defense**: Replace the guard `last_result != Accepted` with an explicit "this transition is a `verify_zk` action firing into the accept branch" — e.g. add an action tag like `last_action` (as `handshake.qnt` does at line 95) and write `next(last_action) == ActVerifyZk and next(last_result) == Accepted`. The current guard is a proxy that fails as soon as `Accepted` becomes idempotent.

## 3. `next(last_input.attestation.variant) == Zk` is necessary but not sufficient evidence the Zk path actually ran

- **Category**: Refinement mismatch
- **Severity**: serious
- **Scenario**: Imagine a future action `replay_last_input` that re-sets `last_input' = some_old_zk_input` without running any verification (e.g. for auditing). If that action also sets `last_result' = Accepted` (a refactor someone might do thinking "auditor accepts replayed valid Zk messages"), then `next(last_input.attestation.variant) == Zk` is true and `next(last_result) == Accepted` is true, but `verify_zk` was never invoked — the pre-transition vkey state may or may not satisfy the RHS. More directly today: in the current spec, the only way to set `last_input.attestation.variant = Zk` AND `last_result = Accepted` simultaneously is via `verify_zk`, so the property holds, but the property's *evidence link* between "Zk variant in last_input" and "the Zk verifier accepted this message" is a coincidence of the current action set, not a structural fact.
- **Why it succeeds**: The intent at `CLAUDE.md` line 8-9 specifies the Zk acceptance path as "TDX quote → zkdcap Groth16 proof → Xion ZK module ... → accept". The temporal property substitutes a state-observation (`last_input.attestation.variant == Zk`) for an action-tag (`verify_zk fired and reached its accept branch`). State-only encodings of action obligations are exactly the trap the comment at lines 387-396 says it is dodging — yet the temporal property re-introduces it in a different form.
- **Suggested defense**: Introduce a `last_action` variable as in `handshake.qnt` (line 95), tag every `verify_zk` outcome with `ActVerifyZk`, and write `(next(last_action) == ActVerifyZk and next(last_result) == Accepted) implies ...`. This makes the action provenance load-bearing instead of inferred.

## 4. `config` is held constant by `verify_zk` — the property checks the wrong state

- **Category**: Temporal-state mismatch
- **Severity**: serious
- **Scenario**: The property at lines 418-424 reads `config.zkdcap_vkey != ""` in the *pre-transition* state. In `verify_zk`'s success branch (line 261), `config' = config` — so the pre-transition and post-transition values are identical. The comment at lines 410-412 claims temporal encoding is "robust against subsequent `clear_vkey` actions that would otherwise invalidate a state-only check". But the property only inspects the state at the moment of the transition; a `clear_vkey` issued *after* a successful `verify_zk` is invisible to the antecedent (because `last_result == Accepted` at that point, so the antecedent `last_result != Accepted` is false). Conversely, a `clear_vkey` issued *before* `verify_zk` would set `config.zkdcap_vkey = ""`, which `verify_zk` would catch at line 225 and never reach `Accepted`. So the "robust against subsequent clear_vkey" framing in the comment is misleading: there is no scenario where a subsequent `clear_vkey` could invalidate the state check. The temporal encoding solves a non-problem; the state-only invariant `inv_zk_accept_requires_vkey = true` could be tightened to `last_result == Accepted implies (config.zkdcap_vkey != "" and registered_vkeys.contains(...))` *for as long as `clear_vkey` is the only mutator* — which it is. The comment at lines 388-396 says this state-only form is impossible because "clear_vkey can run after the verify and last_result is a frozen past decision"; but the temporal form has the *same* limitation, just phrased differently.
- **Why it succeeds**: Lines 388-396 motivate the temporal property by claiming the state-only check fails. Lines 410-412 elaborate this as "robust against subsequent `clear_vkey` actions". Inspect: a subsequent `clear_vkey` step preserves `last_result == Accepted`, so the temporal property's antecedent (line 419 `last_result != Accepted`) is false at that step and the property is vacuously satisfied — the exact same vacuity the state-only form would experience. The temporal property gains nothing over a state-only check at the moment of transition; both check pre-`verify_zk` state. The justification text is therefore wrong.
- **Suggested defense**: Either delete the temporal property and replace `inv_zk_accept_requires_vkey` with a state-only check on `last_input.attestation.variant == Zk and last_result == Accepted`, or rewrite the comments at 388-396 and 410-412 to remove the false "frozen past decision" rationale.

## 5. The property is silent on `registered_vkeys` mutating between `verify_zk` and the witness step

- **Category**: Coverage gap
- **Severity**: serious
- **Scenario**: The spec exposes `zk_module.registered_vkeys` and `zk_module.accept_all` as mutable state but provides only `enable_mock` as a mutator. There is no `register_vkey`, `unregister_vkey`, or `disable_mock` action. The intent at `CLAUDE.md` line 11 says "`zkdcap_vkey` field in Config — name of the verification key registered in Xion's ZK module" — i.e. the vkey set lives in a separate module that can register/unregister keys independently of the contract's `config`. The temporal property witnesses `registered_vkeys.contains(config.zkdcap_vkey)` in the pre-transition state, but does not address: what if the vkey was registered at `verify_zk` time, then unregistered by the ZK module after acceptance? The contract's `last_result == Accepted` is now backed by a vkey that no longer verifies — and the spec has no model of this. This is a coverage gap, not a triviality, because the intent explicitly identifies the ZK module as a separate trust domain (see `crates/contracts/core/src/handler/execute/attested.rs` per `CLAUDE.md`'s "Key files" list).
- **Why it succeeds**: Spec lines 76-79 model `registered_vkeys` as a `Set[VKeyName]`, the only mutator is `init` (line 139) and there's no action that adds or removes vkeys post-init. The intent depends on Xion's ZK module behavior, which is external. The temporal property's RHS pins on `registered_vkeys` at transition time but the spec admits no transitions that change `registered_vkeys`, so the witness is trivially preserved by the spec but not by reality.
- **Suggested defense**: Add a nondeterministic `register_vkey(v)` and `unregister_vkey(v)` action in `step`, and either (a) accept that the temporal property only guarantees vkey state *at acceptance time*, documenting this explicitly, or (b) strengthen the property to a "from acceptance time forward, the vkey remains registered" form using `always(eventually ...)` or a history variable.

## 6. `last_input.attestation.variant` may be `Zk` while the prior step's result is also `Accepted` from a `Quote`-variant in a different scenario — antecedent is brittle

- **Category**: Edge case
- **Severity**: cosmetic
- **Scenario**: The `Quote` variant produces `AcceptedQuote`, not `Accepted` (line 189), so today the variants are partitioned by outcome. But suppose a refactor consolidates `Accepted` and `AcceptedQuote` into a single `Accepted` (a plausible future change since `inv_variant_outcome_consistent` at lines 369-384 already encodes them as a single allowed-set). Then the antecedent `next(last_input.attestation.variant) == Zk` would still correctly filter, but the property's RHS — `config.zkdcap_vkey != "" and registered_vkeys.contains(...)` — is now load-bearing for *every* `Accepted`, not just Zk ones, yet the antecedent excludes Quote acceptances. A Quote-variant acceptance with `clear_vkey` previously called would not be witnessed. This is a refactor hazard, not a current bug.
- **Why it succeeds**: The naming asymmetry `Accepted` vs `AcceptedQuote` (lines 82-83) is non-obvious. The property at line 421 distinguishes Zk via `last_input.attestation.variant`, not via the `last_result` value being specifically the Zk-only `Accepted` constant.
- **Suggested defense**: Rename the result constants to `AcceptedZk` and `AcceptedQuote` and have the property switch on `next(last_result) == AcceptedZk`, removing the dependency on `last_input.attestation.variant`.
