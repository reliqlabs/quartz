VERDICT: BREAKS

The eight `_negl` lifts are technically proven and the `_classical` re-exports honestly preserve the classical chain, but the lifts themselves do not state the property the methodology claims. Every `_negl` theorem in the four `ProtocolVCVio*` files reduces to the same content-free schema: "if `<freshly-introduced opaque function> ≤ Σ <freshly-introduced opaque functions>` pointwise, and each summand is `negligible`, then the LHS is `negligible`." There is *no* semantic link between the LHS advantage function and the actual protocol-fail event the comments describe. Eleven attacks below, three critical, five serious, three advisory.

---

## 1. The protocol-fail advantage is a free function symbol — the lift is a tautology of `negligible_of_le` + `negligible_add`

- **Category**: Triviality / vacuous-conclusion (uniform across all 8 lifts; root cause)
- **Severity**: critical
- **Scenario**: Pick `verifyGroth16_yields_decoded_negl` at `ProtocolVCVio.lean:537`. The theorem statement binds `protocolFailAdv : Groth16SoundAdv → ℕ → ℝ≥0∞` as an arbitrary function with no defining equation, no measure-theoretic content, and no tie to either `verifyGroth16` or `verifyTdxQuote`. The hypothesis `h_bound : ∀ n, protocolFailAdv 𝒜 n ≤ adv 𝒜 n` is satisfied by `protocolFailAdv := fun _ _ => 0`. Under that instantiation the conclusion `negligible (protocolFailAdv 𝒜)` reduces to `negligible 0`, which is `negligible_zero` (line 33 of `Negligible.lean`). The same holds for `handshake_sound_negl` (`handshakeFailAdv := 0`), `handshake_binds_ecies_key_negl` (`bindsFailAdv := 0`), `session_confidentiality_negl` (`confFailAdv := 0`), `session_confidentiality_via_extractor_negl` (`extFailAdv := 0`), `cross_component_transfers_conservation_negl` (`consFailAdv := 0`), `cross_component_auction_winner_determinism_negl` (`auctFailAdv := 0`), and the terminal `cross_component_session_bind_negl` (`bindFailAdv := 0`). The eight `_negl` lifts collectively prove *one* fact: "the negligible class is closed under pointwise domination and finite sums". They prove nothing about Quartz.
- **Why it succeeds**: The classical theorems each have a load-bearing conclusion of the form `Accepted h → ∃ q, was_signed_by_dstack q ∧ …` (e.g. `Handshake.lean:64` for `handshake_sound`). The lift was supposed to replace that conclusion with a probability statement of the form `Pr[verify accepts ∧ ¬ ∃ q, …] ≤ Σ <bundle advantages>`. The Step 6.0 docstring at lines 506-510 of `ProtocolVCVio.lean` explicitly says "the probability that `verifyGroth16 zkdcapVKey proof inputs = true ∧ ¬ ∃ mr ud, verifyTdxQuote (inputs_to_quote inputs) = some (mr, ud)` is bounded by the Groth16 soundness advantage" — but the `theorem` declaration at line 537 binds `protocolFailAdv` as a *free* parameter rather than *defining* it as that probability. The Lean kernel cannot tell the difference; the proof typechecks because `negligible_of_le` only needs a pointwise bound, not a semantic match. The methodology ledger entry at line 12 claims "the lift's parametric negligibility hypothesis is honest"; the lift achieves vacuous honesty by saying nothing.
- **Suggested defense**: Each `_negl` must define `protocolFailAdv` (resp. `handshakeFailAdv`, etc.) as a *concrete* function — either via `evalDist`/`Pr[…]` over the adversary's `ProbComp` output composed with the actual protocol-fail predicate, or as an abbreviation that mentions `verifyGroth16`, `verifyTdxQuote`, `Accepted`, etc. The current free-symbol formulation is a placeholder masquerading as a theorem. The honest version requires the `[Fintype]` carrier refinement the docstrings repeatedly defer (e.g. `ProtocolVCVio.lean:419-420`); until that exists, the lifts should not be claimed as content-bearing proofs. A truthful interim form is `theorem … : True := trivial` annotated with the deferred status, or a `def`/`theorem` pair where the def fixes the fail-advantage and the theorem proves the bound *given* the def.

## 2. The `h_bound` hypothesis is a "Trojan-horse" — it lets the user prove negligibility of any function whatsoever

- **Category**: Hypothesis smuggling
- **Severity**: critical
- **Scenario**: Consider `cross_component_session_bind_negl` (`ProtocolVCVioQuad.lean:370`). Pick any function `f : ℕ → ℝ≥0∞` whose negligibility you want to claim — including functions that are *not* in fact negligible. Instantiate `bindFailAdv := fun _ _ => f n` (use a closure over `n` via the second argument). To produce `h_bound`, you must exhibit five negligibility witnesses on the right-hand side. Pick `groth16KSAdv := fun _ _ => f n`, and `circuitEqAdv`, `tdxAdv`, `hashAdv`, `hashBAdv := fun _ _ => 0`. Then `h_bound` holds with equality on the first summand; you must also supply `h_groth_ks_negl : negligible (groth16KSAdv 𝒜_groth_ks)` — which is `negligible f`, the very fact you wanted to "prove". The conclusion gives you `negligible (bindFailAdv 𝒜)` = `negligible f`. So the lift's logical content is `negligible f → negligible f` — a tautology disguised as a five-summand reduction. The same hole exists in all 8 lifts.
- **Why it succeeds**: The Step 6.0 plan called for the protocol-fail advantage to be *defined* (in terms of the underlying probabilistic experiment) and the cryptographic-assumption advantages to be *named* (in terms of the bundled axioms). The actual lift inverts both directions: protocol-fail is left free, and the bundle advantages are *also* left free (`Groth16SoundAdvantage` and friends are just `abbrev … : Type := Adv → ℕ → ℝ≥0∞` at `ProtocolVCVio.lean:432`, etc., with no link to `groth16Verifier.sound`). The chain of typed function-symbol stubs lets the caller pick any pointwise-dominating function family on either side; `negligible_of_le` does the rest.
- **Suggested defense**: Tie each `*Advantage` `abbrev` to the actual probability event in the corresponding companion module. `Groth16SoundAdvantage` should be `fun 𝒜 n => Pr[verifyGroth16 zkdcapVKey (𝒜 n).1 (𝒜 n).2 = true ∧ ¬ was_signed_by_dstack (inputs_to_quote (𝒜 n).2)]` (or its `evalDist`-bind expansion). With that link, the user cannot pass off an arbitrary `negligible f` hypothesis as the Groth16 soundness assumption — it must be a hypothesis *about the actual Groth16 verifier*. The current Type-only abbreviation pattern is responsible for the smuggling.

## 3. `cross_component_session_bind_negl` does not constrain the reduction — `𝒜_groth_ks`, `𝒜_circuit`, `𝒜_tdx`, `𝒜_hash`, `𝒜_hashB` are five free adversaries unrelated to `𝒜`

- **Category**: Reduction-relation absence (the load-bearing terminal lift)
- **Severity**: critical
- **Scenario**: `cross_component_session_bind_negl` at `ProtocolVCVioQuad.lean:370-400` takes six adversaries — `𝒜 : CrossSessionBindAdv` plus five "underlying" adversaries `𝒜_groth_ks`, `𝒜_circuit`, `𝒜_tdx`, `𝒜_hash`, `𝒜_hashB` — and proves a bound parametric on all six. No part of the statement constrains the five bundle-attack adversaries to be *derived from* `𝒜`. In a real reduction proof, `𝒜_groth_ks` would be a concrete `OracleComp`-program that simulates `𝒜`'s view and extracts a Groth16 KS attack from its output; here it is just an arbitrary `ℕ → ProbComp (VKey × Groth16Proof × PublicInputs)`. So even if every one of the five bundle assumptions is negligible *for adversaries derived from the actual cross-session-bind game*, the lift does not let us conclude anything about the actual `𝒜`. A real adversary against `cross_component_session_bind` is free; the user can pick five completely unrelated 0-advantage `𝒜_*` instances and prove negligibility of any pointwise-dominated `bindFailAdv`. The "real reduction-based proof" claim in the docstring at line 326 is false — there *is* no reduction; the `reduce : … → …` function exists only in `crossSessionBindGame_secure_of_quad_bundle_secure` at line 462, but its image is *not* required to match the bundle-attack adversaries that satisfy `h_bound`.
- **Why it succeeds**: A real cryptographic reduction has a structural shape: given an adversary `𝒜` against the high-level game, *construct* `𝒜_low := reduce 𝒜` against the low-level assumption, *prove* a pointwise relation between `advantage 𝒜` and `advantage (reduce 𝒜)`, then close by reduction monotonicity. In `crossSessionBindGame_secure_of_quad_bundle_secure` the `reduce` parameter exists but its image is only used in `h_bound`'s RHS — there is no requirement that the `reduce` constructed inside `h_bound` corresponds to the *only* way to bound `bindFailAdv 𝒜`. The user supplies `h_bound` directly; the reduce function is just a notational placeholder. Even `crossSessionBindGame_secure_of_quad_bundle_secure` (`ProtocolVCVioQuad.lean:462`) does not constrain `reduce` semantically — it just uses `(reduce A).1` etc. as labels for the five free games. There's no `reduce_correct : ∀ A n, bindFailAdv A n ≤ sum_of_advantages_at_reduce_A_n` reduction-soundness lemma.
- **Suggested defense**: Replace `𝒜_groth_ks`, `𝒜_circuit`, `𝒜_tdx`, `𝒜_hash`, `𝒜_hashB` and `bindFailAdv` with *functions* `𝒜 ↦ 𝒜_groth_ks(𝒜)`, etc. — i.e. derived adversaries — and define `bindFailAdv` as the actual win-probability of `𝒜`. With those, the union bound becomes a real reduction, not a parametric trapdoor. The terminal lift is the load-bearing one per the ledger (line 80 "load-bearing terminal lift"); this is the single highest-leverage place to fix.

## 4. The `(d-disjunction-vs-decomposition)` expansion at the terminal lift is cosmetic — the disjunction is collapsed back into a single free symbol

- **Category**: (d-disjunction-vs-decomposition) collapse — Methodology v0.2 ask 4
- **Severity**: serious
- **Scenario**: Ledger Methodology ask 4 (lines 237-238) says `groth16Verifier`'s doubled-negligibility (Groth16-KS ∨ circuit-equivalence) must *expand* at the terminal lift. `cross_component_session_bind_negl` (`ProtocolVCVioQuad.lean:370`) does split the bound into `groth16KSAdv 𝒜_groth_ks n + circuitEqAdv 𝒜_circuit n` (two summands instead of one). But the semantic expansion the ask was asking for would relate `groth16Verifier.sound`'s actual classical-Prop statement to a disjunction of "Groth16 KS adversary wins OR circuit-equivalence breaks", and bound the corresponding events. Here, both `Groth16KSAdvantage` and `CircuitEqAdvantage` are again opaque `Type := Adv → ℕ → ℝ≥0∞` aliases (lines 211 and 232), neither tied to the `verifyGroth16` semantics nor to `inputs_to_quote`. Calling them "decomposed" relies on the *adversary type* changing (`CircuitEqAdv = ℕ → ProbComp PublicInputs` at line 228, vs. `Groth16SoundAdv = ℕ → ProbComp (Groth16Proof × PublicInputs)` at `ProtocolVCVio.lean:406`) — but since neither advantage abbrev mentions the protocol, the decomposition is cosmetic. The lift could equally well have been left collapsed into a single `Groth16SoundAdvantage` and the proof would still go through.
- **Why it succeeds**: The `(d-disjunction-vs-decomposition)` ask exists to surface the fact that two *independent* cryptographic primitives are jointly load-bearing. The methodology test is whether an external auditor reading the terminal lift can see both KS and circuit-equivalence as separately-named, separately-discharged assumptions. They can see the names — but the lift offers no machinery for an auditor to verify that an attack on either underlying primitive lifts to a `cross_component_session_bind` failure. The decomposition is type-level only.
- **Suggested defense**: The Groth16 KS adversary should be required to produce a `(VKey × Groth16Proof × PublicInputs)` for which the *Groth16 verifier* accepts but the *R1CS witness* doesn't exist; the CircuitEq adversary should produce a `PublicInputs` for which the *R1CS circuit's output* differs from the *reference DCAP verifier's* on the corresponding quote. The current adversary types have the right *shape* (lines 207, 228) but their advantage functions don't mention any of these conditions. Strengthen the advantage `abbrev`s into `def`s with concrete win-condition predicates.

## 5. The `IsPPT := True` placeholder makes the `*Game_secure_of_*_bundle_secure` packagings *worse* than the plain `_negl` forms

- **Category**: `IsPPT := True` placeholder vacuity (Methodology v0.2 ask)
- **Severity**: serious
- **Scenario**: Look at `handshakeSoundnessGame_secure_of_dual_bundle_secure` (`ProtocolVCVioDual.lean:306-321`). It quantifies over `A : HandshakeSoundAdv` with `_hA : IsPPT A` (after unfolding the implicit). With `IsPPT := True` at `ProtocolVCVio.lean:288`, this quantification reduces to "for all `A`" — so the SecurityGame conclusion `secureAgainst IsPPT` is "for all adversaries, negligible advantage" rather than "for all PPT adversaries, negligible advantage". The classical security definition is over *PPT* adversaries; the lift's "for all adversaries" is *stronger* — and that's a problem, because it means a security proof that the lift produces is *more* demanding than the real-world assumption can supply. Combined with attack 2 (free-symbol advantages), the user can trivially produce a "secure against all adversaries" certificate that means nothing. The ledger acknowledges this at line 268 ("PolyQueries adoption a blocker"), but the placeholder is currently allowed to claim a stronger property than the classical statement.
- **Why it succeeds**: Real `secureAgainst` filters by `isPPT`. With `isPPT := True`, the filter is removed; the universal quantifier ranges over *all* (including unbounded) adversaries. The honest statement of cryptographic security against PPT adversaries cannot in general be promoted to security against unbounded adversaries — for unbounded adversaries, knowledge soundness and TDX-quote unforgeability are *false* (an unbounded adversary can break BN254 in finite time). Either the lift's bundle-secure hypotheses are *also* over-strong (and hence un-discharge-able), or the conclusion is over-strong; in either case, the placeholder makes the lift dishonest in a direction the ledger flags but does not currently block.
- **Suggested defense**: At minimum, the `SecurityGame` form should not be claimed as a usable export until `IsPPT` is tightened. The `_negl` form (the bare `negligible (failAdv 𝒜)` statement) is closer to honest because it only mentions one adversary and doesn't claim a universal quantifier — but it still suffers from attacks 1-3. Document the placeholder gap *in the theorem name*, e.g. `handshakeSoundnessGame_secure_of_dual_bundle_secure_AGAINST_UNBOUNDED_ADVERSARIES` until `PolyQueries` adoption.

## 6. The lifts smuggle in adversaries that take *no oracle access* — the `ProtocolSpec` is defined but never used

- **Category**: Carrier-refinement smuggling / definition ambiguity
- **Severity**: serious
- **Scenario**: `ProtocolSpec` is defined at `ProtocolVCVio.lean:200-202` as the `(+)`-sum of the five companion `OracleSpec`s. The intent (per the docstring) is to model adversaries that can query the protocol's oracles. Every single adversary `def` in the four ProtocolVCVio*.lean files instead uses `ProbComp` — i.e. `OracleComp unifSpec`, an oracle-comp over the *uniform-randomness* spec only, with no `ProtocolSpec` queries available. E.g. `Groth16SoundAdv := ℕ → ProbComp (Groth16Proof × PublicInputs)` at `ProtocolVCVio.lean:406`; same shape for `TdxVerifierSoundAdv` (`ProtocolVCVioDual.lean:133`), `HandshakeSoundAdv` (`ProtocolVCVioDual.lean:173`), and so on through to `CrossSessionBindAdv` (`ProtocolVCVioQuad.lean:256-257`). The adversary cannot adaptively query `commitHashOC`, `verifyTdxQuoteOC`, or `verifyGroth16OC` — its only randomness is its own internal coin flips. Real cryptographic adversaries against a Groth16 verifier *do* get to query the verifier on adaptively-chosen `(proof, inputs)` triples before producing their forgery; a no-oracle-access adversary is strictly weaker, and a soundness bound against no-oracle-access adversaries does *not* imply the same bound for oracle-access adversaries. The "ProtocolSpec" infrastructure is decorative.
- **Why it succeeds**: `ProtocolSpec` is exported but never appears in any adversary type, advantage `abbrev`, or theorem statement after its declaration. The companion `OracleSpec`s (`CommitHashSpec`, `VerifyGroth16Spec`, etc.) are likewise unused in the four protocol-side modules. The companion modules' `*OC` definitions (e.g. `verifyGroth16OC` at `ZkdcapVCVio.lean:202`) are similarly never invoked in the lifts. The lifts hand-roll their own `ProbComp`-based adversaries that look like they fit VCV-io's oracle-access framework but in fact bypass it.
- **Suggested defense**: Either (a) admit explicitly that the current lifts are over no-oracle-access adversaries and rename the adversary types accordingly (`HandshakeSoundAdv_no_oracle`), and document that the framework upgrade to oracle-access adversaries is required before any composition reduction is honest; or (b) actually make the adversary types `OracleComp ProtocolSpec`-valued and re-prove the lifts. Option (a) is honest about the gap; the current setup *implies* (by importing `ProtocolSpec`, by using the term "PPT", by using `SecurityGame.secureAgainst`) that the framework is in scope when it is not.

## 7. `_classical` re-export for `cross_component_session_bind` carries a dependency the ledger does not flag at the `_negl` level

- **Category**: Composition-step axiom leakage — verify-by-inspection invariant
- **Severity**: serious
- **Scenario**: The ledger line 74 lists for `cross_component_session_bind_negl`'s `_classical` closure: `commitHashE + commitHashBytesE + tdxVerifier + groth16Verifier + carriers + rawBoundContract, rawDomainSep, serializeRawSessionSetPubKeyE, userDataOfSessionSetPubKey_eq_commitHash, was_signed_by_dstack, keyOf`. The ledger's "invariant across all 8 lifts" claim (line 76) says `_negl` closures hide bundle axioms uniformly. The methodology brief at the top of this attack file flags ask 4 about disjunction-decomposition, and ask 3 about `commitHashE`/`commitHashBytesE` framing. None of the asks flag that `userDataOfSessionSetPubKey_eq_commitHash` (an axiom per the ledger row 16, classified `(c)` as a "genuine bridge equality") is *still* in the `_classical` closure of the terminal lift, but the `_negl` form silently drops it. If the `_negl` form claims to model the same trust statement as the classical, and the `_classical` requires `userDataOfSessionSetPubKey_eq_commitHash` to connect `userDataOfSessionSetPubKey raw` with `commitHash` of the structured commit, then the `_negl` form is incomplete: it does not even *mention* this bridge, much less bound its failure probability. The bridge is a "genuine" bridge (ledger row 16, classified `(c)`), but its truth at run time requires a constructive serde_json model that does not yet exist. The lift hides this dependency from the `_negl` closure not because it has been discharged, but because the lift does not state any condition that would invoke it.
- **Why it succeeds**: The `_negl` form does not mention `cross_component_session_bind`'s conclusion at all (per attack 1). So it cannot mention any of the lemmas that classical proof uses — `userDataOfSessionSetPubKey_eq_commitHash`, `pkOfUserData_commitHash`, etc. Hiding axioms from the closure is technically true but trivially so: a theorem stating "if X is negligible then X is negligible" trivially has no axiom closure beyond standard logic, even when the real semantic content requires those axioms.
- **Suggested defense**: The "ledger reviewer checklist" item at line 218 ("All 8 `_negl` closures verified to carry **no bundle axioms**?") is meaningless given attack 1; it's only true because the `_negl` forms say nothing. Reframe the invariant: a `_negl` lift's closure should contain *exactly* the axioms the `_classical` form contains *minus* the bundle axiom shadowed by the parametric negligibility hypothesis. The current uniform invariant is satisfied vacuously.

## 8. Option-(b) framing for `commitHashE`/`commitHashBytesE` doesn't restate the hypothesis — it restates *nothing*

- **Category**: (d-vacuous-hypothesis) violation — Methodology v0.2 ask 3
- **Severity**: serious
- **Scenario**: The ledger ask 3 (line 235) says `commitHashE` and `commitHashBytesE` are spec-impossible (pigeonhole) and the lift must "restate the truthful cryptographic hypothesis (collision resistance of the concrete real-world hash)". The `_negl` lifts introduce `CommitHashCollisionAdv := ℕ → ProbComp (UserDataCommit × UserDataCommit)` (`ProtocolVCVioTriple.lean:193-194`) and the advantage abbrev `CommitHashCollisionAdvantage := CommitHashCollisionAdv → ℕ → ℝ≥0∞` (line 209-210). The advantage abbrev is again an opaque `Type` alias — no `def` ties it to `commitHash : UserDataCommit → UserData` (which is itself `commitHashE.toFun` per the bundle axiom). So the "collision resistance hypothesis" is a parametric `negligible (hashAdv 𝒜_hash)` where `hashAdv 𝒜_hash` is *any* function. The intended interpretation — "the probability that `𝒜_hash n` outputs `(uc₁, uc₂)` with `uc₁ ≠ uc₂ ∧ commitHash uc₁ = commitHash uc₂` is negligible" — is in a *docstring comment* at lines 199-203, not in the type. So the Option-(b) framing has the same vacuity as the rest: the user can pick `hashAdv := fun _ _ => 0` (no collision attack) and the negligibility hypothesis is trivially true, regardless of whether the *real* hash function is collision-resistant. The lift's collision-resistance hypothesis does not constrain the real hash.
- **Why it succeeds**: The methodology test for the (d-vacuous-hypothesis) finding is: does the lift upgrade the impossible-as-stated injection axiom into a non-vacuous cryptographic hypothesis? The lift names a new symbol `hashAdv` and says it is negligible, but does not connect that symbol back to `commitHash`. A non-vacuous restatement would be `negligible (fun n => Pr[(uc₁, uc₂) ← 𝒜_hash n; pure (uc₁ ≠ uc₂ ∧ commitHash uc₁ = commitHash uc₂)])` (or its `evalDist` expansion). The lift could even sidestep `Pr[…]` by an axiomatic predicate `IsCollisionResistant (h : UserDataCommit → UserData) (𝒜 : CommitHashCollisionAdv) : Prop` defined in the companion module, and require that predicate as the hypothesis. The current setup names nothing.
- **Suggested defense**: Define `commitHashCollisionAdvantage : CommitHashCollisionAdv → ℕ → ℝ≥0∞` as a *function* (not a Type abbreviation) computing the actual collision probability against the actual `commitHash`. Same for `commitHashBytesCollisionAdvantage`. The companion modules `UserDataCommitVCVio.lean` and `RawMessagesVCVio.lean` already sketch this in informal commentary (per the ledger row 8); promote the comments to definitions.

## 9. The 5-summand union bound is independent-summed — correlations across the SHA-256-derived bundles are not accounted for

- **Category**: Hypothesis correlation
- **Severity**: serious
- **Scenario**: `commitHash` and `commitHashBytes` are both real-world SHA-256-keyed hashes per the project intent (per `crates/enclave/core/src/encryption.rs` and the underlying enclave code, which use SHA-256 throughout). A real adversary attacking both `commitHashE` and `commitHashBytesE` is attacking the *same* underlying hash primitive with two *different* input encodings. Collisions in one are not independent of collisions in the other — a collision-finder on SHA-256 inputs of one shape may be re-purposed on inputs of another shape with no efficiency loss, and a meaningful break of SHA-256 collision resistance triggers both budgets simultaneously. The union bound at `ProtocolVCVioQuad.lean:383-386` sums the two advantages as if they were independent. They are not. The same observation applies to `negligible_groth16_ks` and `negligible_circuit`: the former relies on BN254 group hardness assumed for a specific R1CS shape, the latter on circuit-equivalence against that same R1CS shape — a bug in either circles back to the same generator setup. The five summands are not five independent advantages.
- **Why it succeeds**: A union bound is sharp when the underlying events are *disjoint*; it is loose when they overlap, and *wrong* (in the asymptotic sense) when they are positively correlated by a factor that scales with the security parameter. The lift uses `negligible_add` which is just "sum of negligibles is negligible" — a correct fact, but only useful when the summands genuinely model independent adversary classes. Treating commitHashE and commitHashBytesE collisions as independent is a modelling choice that hides the real attack path: if SHA-256 collision resistance breaks, *both* summands break simultaneously, and the union bound conceals the doubling. For asymptotic negligibility this is OK in the limit; but for concrete-security claims (which the ledger says are eventually the discharge path via `randomOracle` birthday bound) it's incorrect.
- **Suggested defense**: Add a comment to the terminal lift explaining the independence assumption; ideally introduce a *joint* SHA-256 collision-resistance assumption with a single negligibility hypothesis, of which both `commitHashE` and `commitHashBytesE` are reductions. The current setup is asymptotically OK (since two negligibles still sum to a negligible) but suggests a tighter bound than exists.

## 10. `was_signed_by_dstack`'s `Classical.propDecidable` instance is `noncomputable local` — `Pr[…]` over it is meaningless

- **Category**: Definition / theorem ambiguity (`Pr[…]` measurability)
- **Severity**: advisory
- **Scenario**: At `ProtocolVCVio.lean:368-370`, a `noncomputable local instance` is added to make `was_signed_by_dstack q` `Decidable` via `Classical.propDecidable`. The docstring at lines 354-367 says this is to let `Pr[…]` "type-check". But in VCV-io, `Pr[…]` is `evalDist`-based; the `Decidable` instance gives only the syntactic form. The actual probability is well-defined only if `evalDist` reaches a measurable event, and `Classical.propDecidable` makes the predicate decidable in *classical logic* without giving any computational handle. For the abstract carrier `TdxQuote` the resulting event-set has no finite description, so even `evalDist (do let q ← 𝒜 n; pure (was_signed_by_dstack q))` lacks a concrete distribution. The `Pr[…]` form referenced in the docstring at line 415 is informal-only.
