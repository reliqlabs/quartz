## 1. [ranked-choice] `find_loser` eliminates the WRONG candidate — spec inverts the Rust tie-break direction

- **Target spec**: `ranked-choice.qnt` lines 176-190 (`find_loser`) and 394-419 (`inv_deterministic_tiebreak`).
- **Category**: Spec-vs-implementation drift / tie-break correctness — load-bearing for IRV winner correctness
- **Severity**: **critical**
- **Scenario**: `enclave/src/request.rs:93` sorts the count vector with `count_vec.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(&b.0)))` — votes DESCENDING, then within equal-vote groups, name ASCENDING. So `count_vec` looks like `[(3, "Alice"), (3, "Bob"), (1, "Carol"), (1, "Dave")]` (high-votes first, then lex-ascending names). Line 137-143 then computes the loser by `count_vec.iter().rev().find(|(_,v)| *v == min_votes).unwrap().0.clone()`. `.iter().rev()` traverses the vector backwards, so among min-vote entries it yields the alphabetically LARGEST name first (Dave before Carol in the example). `find` returns that — so the Rust eliminates the **lexicographically LARGEST** candidate among those tied for fewest votes. The Quint `find_loser` at lines 182-190 returns the lex-SMALLEST: `if (counts.get(c) == min_v and (acc == "" or lex_lt(c, acc))) c else acc`. The docstring at lines 176-181 explicitly claims the opposite of what the Rust does ("we scan from the back and pick the first min-vote entry — i.e. the lexicographically smallest name among the losers"). The reasoning step in that docstring is wrong: scanning from the back of a name-ASCENDING-sorted run yields the LARGEST name first, not the smallest. Concrete reachable trace with the bounded universe of 2 voters / 3 candidates: voter `v1` casts `[BOB]`, voter `v2` casts `[CAROL]`. Round-1 counts: ALICE=0, BOB=1, CAROL=1. min_votes=0; only ALICE is at min, no tie — fine. Now: `v1` casts `[ALICE]`, `v2` casts `[BOB]`. Round-1 counts: ALICE=1, BOB=1, CAROL=0. min_votes=0; only CAROL at min — also no two-way tie. To exercise the tie: `v1` casts `[CAROL]`, `v2` casts `[CAROL]`. Round-1 counts: ALICE=0, BOB=0, CAROL=2. CAROL has majority, no elimination. Hmm — try `v1` casts `[ALICE, BOB, CAROL]`, `v2` casts `[BOB, ALICE, CAROL]`. Round-1: ALICE=1, BOB=1, CAROL=0. CAROL alone at min, no tie. To get a 2-way tie at min, need 2 candidates each with 0 votes — possible with both voters voting for the same candidate via exhausted prefixes, e.g. `v1` = `[ALICE]`, `v2` = `[ALICE]`. Counts: ALICE=2, BOB=0, CAROL=0. ALICE has majority and wins; no elimination needed. The 2-voter/3-candidate universe makes a min-vote tie *with elimination needed* hard to exercise — but a 2-voter setup with the 2-candidate election variant `create_election(Set(ALICE, BOB))` and ballots `[ALICE]`, `[BOB]` produces counts ALICE=1, BOB=1, both tied at min=1 = max=1, no majority — and elimination must run. Then `find_loser` Rust: lex-LARGEST = BOB; `find_loser` Quint: lex-SMALLEST = ALICE. Round 2: after BOB eliminated (Rust) the remaining is ALICE — winner ALICE. After ALICE eliminated (Quint) the remaining is BOB — winner BOB. The Quint spec's `inv_winner_satisfies_irv` (line 378-383) will accept BOB as the IRV winner, but the Rust will report ALICE. The spec models a different protocol from the implementation.
- **Why it succeeds**: The docstring lines 176-181 contains an off-by-one inversion: it says "scan from the back and pick the first min-vote entry" then concludes "i.e. the lexicographically smallest name among the losers". The first part describes the Rust code correctly; the second part draws the wrong conclusion from it. The Quint implementation matches the (wrong) conclusion, not the (correct) intermediate step. Both the Quint `find_loser` AND the Quint `inv_deterministic_tiebreak` (lines 394-419) bake in this inverted rule, so the invariant is satisfied by the spec but the spec is checking the wrong direction. The bounded universe of `Set(ALICE, BOB)` create_election variant (line 329) does admit traces that exercise the tie at the 2-candidate elimination level, so this is *reachable* in the slimmed state space, not just a refactor hazard. Apalache BMC at depth 7-10 should have detected this — except the Quint `instant_runoff` uses the *same* `find_loser` for its winner computation as the invariant uses for its tie-break check, so both sides of `inv_winner_satisfies_irv` are computed by the same (wrong) function, and the invariant trivially holds. The invariant is consistent with `instant_runoff`'s spec semantics; both diverge from the Rust by the same factor, so the inconsistency is invisible to model checking.
- **Suggested defense**: Flip the predicate in `find_loser`:
  ```
  if (counts.get(c) == min_v and (acc == "" or lex_lt(acc, c))) c
  else acc
  ```
  i.e. keep `c` if `c` is lex-LARGER than the running `acc`. Update the docstring at lines 176-181 to remove the "smallest" claim. Optionally add an explicit test case `inv_tiebreak_matches_rust`: an Apalache witness that for the canonical tie configuration (ALICE=1, BOB=1) the elimination is BOB. Also: the bug propagates to `inv_winner_satisfies_irv` indirectly, but since both sides use the same wrong function, the invariant is hollow until the function is fixed. Re-running Apalache after the fix may surface additional counter-examples in 3-candidate IRV traces if more elimination ties become reachable.

## 2. [ranked-choice] `Tallying` phase is unmodeled — same kind of dormant-enum-variant gap the sealed-auction `Resolving` revision was supposed to fix

- **Target spec**: `ranked-choice.qnt` line 50-53 (`Phase` enum)
- **Category**: Phase-machine completeness / spec-vs-implementation drift
- **Severity**: **critical**
- **Scenario**: `examples/ranked-choice/contracts/src/state.rs:12-17` defines four phases: `Setup`, `Voting`, `Tallying`, `Complete`. `exec_tally` at `contract.rs:160` accepts transitions from BOTH `Voting` AND `Tallying` (mirroring the sealed-auction `Bidding|Resolving` pattern, the very pattern the sealed-auction spec was *just revised* to model). The Quint spec models only three phases — `Setup`, `Voting`, `Complete` — silently flattening `Tallying`. There is no `close_voting` action analogous to the auction's `close_bidding`, and `tally` (lines 304-318) requires `contract.phase == Voting` strictly. Any state the chain reaches with `phase = Tallying` (e.g. an off-chain orchestrator flipping the phase between voting close and enclave attestation) is unrepresented in the spec. This is exactly the smell that the sealed-auction revision (ledger entry: "Sealed-auction spec smells — Resolving phase now wired into the Quint state machine") was supposed to cure across all Quartz example specs, but the ranked-choice spec was not given the same treatment. The ledger explicitly identifies this kind of gap as a "ghost transition path" and lists it as an attack angle for Round B.
- **Why it succeeds**: The phase enum in the Rust contract is the single source of truth for legal on-chain states. `Tallying` is a member of that enum and `exec_tally` permits it as an entry phase. Off-chain agents (the enclave orchestrator, the relayer) may post a `phase = Tallying` transition; the Quint spec's omission of this phase means no invariant can constrain what is allowed during `Tallying`. The slimming note at lines 18-38 documents the dropped state vars but does *not* mention dropping `Tallying` — suggesting this is an oversight rather than a deliberate abstraction.
- **Suggested defense**: Mirror the sealed-auction revision exactly:
  1. Add `Tallying` to the `Phase` enum (line 50-53).
  2. Add a `close_voting` action analogous to `close_bidding` that flips `phase = Tallying` when the voting deadline is past (though note: the contract has no on-chain `close_voting` either — `Tallying` is set by the off-chain enclave orchestrator before posting the attested tally; if the agent decides this is out-of-spec for the chain-level model, document that explicitly).
  3. Allow `tally` to fire from either `Voting` or `Tallying`.
  4. Add `inv_tallying_only_after_deadline` mirroring `inv_resolving_only_after_deadline` at auction lines 467-471.
  5. Update `inv_phase_well_formed` (line 423-428) to include `Tallying`.

## 3. [ranked-choice] `inv_ballot_integrity` rephrase is NOT equivalent to the original — the old form was a temporal invariant; the new form is a stateless type predicate

- **Target spec**: `ranked-choice.qnt` lines 341-359
- **Category**: Equivalence-claim verification (the spec author's claim of equivalence is wrong)
- **Severity**: **serious**
- **Scenario**: The docstring at lines 341-354 says the original invariant was `ballots.get(v) == ballot_history.get(v)` (asserting two parallel maps stay in lockstep). The new form is `ballots.keys().forall(v => ALL_VOTERS.contains(v) and ballots.get(v).length() > 0)`. The author claims these are "structurally equivalent" because `cast_ballot` rejects repeats and the two maps were never mutated independently. This reasoning has two gaps:
  - **(a) Temporal vs. stateless content**: The original was a *correspondence between two state vars across time* — its violation would have detected accidental mutation of a stored ballot (e.g. a buggy `cast_ballot` that overwrites instead of rejecting). The new form is a *type predicate* that catches "the key is one of the bounded universe of voters" and "the ballot is non-empty". A buggy `cast_ballot` that allowed overwriting an existing ballot with a different non-empty ballot from a known voter would *still* satisfy the new invariant. The structural equivalence claim relies on the *current* `cast_ballot` body being correct — but the *point* of invariants is to detect when the body becomes incorrect.
  - **(b) Universe constraint hidden**: `ALL_VOTERS.contains(v)` is enforced by the `step` action's `nondet voter = oneOf(ALL_VOTERS)` (line 325). So `inv_ballot_integrity` is a *consequence* of the step relation in the slimmed spec, not a constraint on it. In the original spec with a `ballot_history` variable, the equivalent assertion `ballots.get(v) == ballot_history.get(v)` was independent of the step constraint — it could be violated by a buggy action even with the step constraint holding. The new invariant degenerates into "yes, the step relation does what step says" rather than "yes, the action preserves the ballot binding".
- **Why it succeeds**: Slimming away `ballot_history` removed the only state that could differ from `ballots`. Without that second variable, the invariant has no *witness* for "the ballot binding was preserved" — only a witness for "no entries from outside the universe and no empty ballots". The two are equivalent *only if* you trust `cast_ballot` to be correct. The original invariant was a check on `cast_ballot`; the new one isn't.
- **Suggested defense**: Either (a) keep the invariant but rename it to `inv_ballot_well_formed` and document that it no longer covers ballot-mutation freshness, OR (b) add a ghost history variable `ballot_history: Addr -> Ballot` that is *only ever* written from inside `cast_ballot` (with no other action modifying it), and assert `ballots == ballot_history` — this restores the original invariant with explicit state cost. Option (b) re-introduces the state-space cost the slimming was meant to avoid, so (a) is likely the right call — but the *equivalence claim* in the docstring must be retracted: the old and new forms are NOT equivalent in the face of `cast_ballot` mutation bugs. The current docstring is misleading.

## 4. [sealed-auction] `close_bidding` is an invented action with no Rust counterpart — phase machine is over-specified

- **Target spec**: `auction.qnt` lines 206-224
- **Category**: Phase-machine completeness / over-specification
- **Severity**: serious
- **Scenario**: `contract.rs` has exactly three execute branches that mutate the auction state: `exec_start_auction`, `exec_submit_bid`, `exec_resolve`. None of them writes `phase = Resolving`. `exec_resolve` jumps from `Bidding|Resolving` *directly* to `Complete` (line 161). There is no on-chain transition into `Resolving`. The Quint spec invents a `close_bidding` action (lines 213-224) that flips `phase: Resolving` once `block_time >= auction_end`. The docstring at lines 206-212 says "Anyone can flip the phase once the deadline is past — it is a pure observable, not an admin-gated transition." This is **false**: there is no execute message that flips the phase, and no automatic transition either. The `Resolving` phase exists in the enum only as an *input* state to `exec_resolve` (per the contract's `phase != Bidding && phase != Resolving` guard), presumably set by some off-chain orchestrator pattern not modeled in `contract.rs`. The Quint spec's `close_bidding` action invents a behavior the contract does not implement; if any invariant relies on `phase == Resolving` being reachable to be non-vacuous, it is reachable only via this invented action.
- **Why it succeeds**: The ledger entry "Resolving phase now wired into the Quint state machine matching the contract's `AuctionPhase::Resolving`" describes the revision as a match against the contract's enum, not against any contract action — and indeed the contract has no action for the transition. The spec captures the *static* enum membership but misrepresents the *dynamic* state machine: `Resolving` is a state that off-chain orchestration may put the chain into, not a state the contract itself can reach via its own execute logic. The Quint spec's `close_bidding` therefore models an external actor's behavior with no on-chain semantics, conflating "reachable in deployment" with "reachable per the contract's transition logic".
- **Suggested defense**: Either (a) delete `close_bidding` and model `Resolving` as an *external* input state — the spec could nondeterministically initialize the phase to `Resolving` for some traces but provide no transition into it, OR (b) document explicitly in the spec header that `close_bidding` models an *off-chain orchestration step* (e.g. the relayer flipping the phase) that is not part of the contract's own transition logic. Right now the spec implies the contract has a close_bidding execute path that doesn't exist.

## 5. [sealed-auction] `inv_resolving_only_after_deadline` is dormant after a non-tick action perturbs block_time relative to auction_end via a new round

- **Target spec**: `auction.qnt` lines 460-471
- **Category**: Dormant invariant / refactor brittleness (analogous to Round-1 S1)
- **Severity**: serious
- **Scenario**: `inv_resolving_only_after_deadline` checks `block_time >= contract.auction_end` whenever `contract.phase == Resolving`. The only action that sets `phase = Resolving` is `close_bidding`, which itself guards `block_time >= contract.auction_end`. So whenever the antecedent is true, the consequent was true *at the moment of the transition*. But: (a) the invariant compares **current** `block_time` against **current** `contract.auction_end`, not against the auction_end captured at the time of the transition. (b) `start_auction` updates `contract.auction_end` to `block_time + AUCTION_DURATION` but only fires from `phase == Idle or phase == Complete` — not from `Resolving`. So `auction_end` cannot be silently lowered while phase is `Resolving` — the invariant holds for sound reasons today. But this is brittle: if a future refactor adds an action like `extend_auction_end` (a feature already implied by the bidder anti-sniping support listed in `CLAUDE.md` for the BidBoard contract) that can fire from `phase == Resolving`, the invariant becomes ill-formed: "auction_end is in the future" is a *type* property the invariant claims to enforce, but the captured-at-action-time analog is what `inv_no_late_bids` already does (with `last_auction_end` book-keeping). The new `Resolving` invariant should follow the same pattern — `last_action == DidCloseBidding implies last_action_block_time >= last_auction_end` — but instead it reads live state. This is the same brittleness pattern as Round-1 S1 (state-only guards refactor-fragile).
- **Why it succeeds**: The pattern `if (contract.phase == Resolving) live_state_check` works only as long as no action transitions phase OUT OF Resolving without also moving auction_end. `resolve` moves phase to Complete but doesn't touch auction_end — fine. `start_auction` moves phase from Idle/Complete to Bidding — fine, it skips Resolving. The invariant is sound today but is one new action away from becoming unsound, and the spec has the bookkeeping (`last_action_block_time`, `last_auction_end`) to defend against it but doesn't use it.
- **Suggested defense**: Rewrite as `if (last_action == DidCloseBidding) last_action_block_time >= last_auction_end`, matching the pattern of `inv_resolve_after_deadline` at lines 422-426. This makes the invariant resilient to future action introduction. Note this is the *exact* fix-pattern Round-1 S1 (`temporal_zk_accept_requires_vkey`) settled on with `last_action == ActVerifyZk`.

## 6. [sealed-auction] `inv_no_premature_reveal` cannot fire on the resolve-from-Bidding path because it requires `enclave.decrypted_bids.keys() != Set()` AND `phase == Complete`

- **Target spec**: `auction.qnt` lines 387-405
- **Category**: Dormant invariant (silent vacuity)
- **Severity**: serious
- **Scenario**: The invariant has two clauses joined by `and`: (i) `contract.phase == Complete`, (ii) `last_action == DidResolve implies last_action_block_time >= last_auction_end`. The antecedent is `enclave.decrypted_bids.keys() != Set()`. Looking at when decrypted_bids is non-empty: only the `resolve` action's else-branch (line 262-289) populates it. After resolve, phase IS Complete and last_action IS DidResolve. So the consequents (i) and (ii) both hold at the moment of resolve. But: in the resolve action's THEN branch (line 247-261, no-valid-bids case), `decrypted_bids' = decrypted_bids` is NOT written — actually, looking at line 242, `enclave' = { ...enclave, decrypted_bids: decrypted }` IS written in both branches because the assignment is *outside* the if/else, at the top of the action body. Wait — re-reading more carefully: line 242 is inside the `all { ... }` block of the resolve action, BEFORE the `if (valid_bids == Set())` at line 247. So `enclave'.decrypted_bids = decrypted` regardless of branch. So even when no valid bids exist, the enclave's decrypted_bids map is populated with the (filtered-by-keys) decrypted values. The invariant fires. But then: after a subsequent `start_auction` (which can run from `phase == Complete` per line 147), the contract phase goes to `Bidding` and `enclave' = { ...enclave, decrypted_bids: Map() }` (line 160). So `decrypted_bids` is cleared on new-round-start. Between resolve and start_auction, the invariant is non-vacuous. Good. But consider: `tick` after resolve. `last_action' = DidTick`. Now `last_action == DidResolve` is false, so clause (ii) is vacuous. The invariant reduces to `phase == Complete`, which is true. So after one tick, the second clause becomes inactive and the invariant lets through any time-evolution that would NOT be caught by clause (ii). Concretely: a hypothetical `extend_auction_end` action that fires from `phase == Complete` and lowers `auction_end` to some value `< last_action_block_time` would still leave clause (ii) inactive (because last_action is no longer DidResolve). The invariant is dormant after the first non-resolve action. This is the same Round-1 S1 brittleness as attack 5.
- **Why it succeeds**: The compound antecedent `last_action == DidResolve` makes clause (ii) a *moment-of-resolve* assertion, not a *persistent-after-resolve* assertion. Once any other action runs, clause (ii) drops out — silently — because `last_action != DidResolve`. The invariant's name and docstring suggest a stronger guarantee ("no front-running / no premature reveal"), but its enforcement window is exactly one transition long.
- **Suggested defense**: Track a `resolve_happened_at: int` ghost variable, written only by `resolve`, never overwritten. Replace the `last_action == DidResolve` guard with `resolve_happened_at > 0 implies resolve_happened_at >= last_auction_end_at_resolve`. This makes the assertion persistent across the lifetime of a round. Alternatively, weaken the invariant docstring to "at the moment of resolve, ..." and accept the narrowness.

## 7. [sealed-auction] `inv_winner_is_highest` lets the spec accept a winner who is not the highest bidder when there are ties

- **Target spec**: `auction.qnt` lines 352-360 + `resolve` lines 263-269
- **Category**: Spec-vs-implementation drift / tie-break correctness
- **Severity**: serious
- **Scenario**: The Rust resolver at `enclave/src/request.rs:61-63` does `decrypted.sort_by(|a, b| b.1.cmp(&a.1))`, then `decrypted[0].0.clone()`. Rust's `sort_by` is **stable**, so when two bidders have equal amounts, the one that was earlier in the input vector wins. The input vector is constructed by iterating `BALLOTS` storage, which is a CosmWasm `Map<&Addr, HexBinary>` — iteration order is by key (lexicographic) by default. So in a tie, the **lex-smallest address** wins. The Kani harness `vickrey_tie_break_lowest_index` at `state.rs:296-304` documents this as "smallest-index tie-break" — but the helper `vickrey_select` keeps the first index on `b > best` (strict), so equal-bid ties default to the lex-smallest *index*, which in the production `resolve_auction` corresponds to lex-smallest *address*. The Quint spec's `resolve` action picks the winner with `valid_bids.fold("", (best_addr, addr) => if (decrypted.get(addr) == max_amount and best_addr == "") addr else best_addr)` — but `fold` over a `Set` in Quint has *unspecified iteration order*. The first address visited that matches `max_amount` wins. Quint's `Set.fold` does not guarantee lex order; it gives "some" order. So the spec's tie-break is **nondeterministic**, while the Rust's is **deterministic by address-lex**. `inv_winner_is_highest` checks only that the winner has at-least-the-max amount, which is satisfied by either bidder in a tie. So the invariant cannot distinguish a Quint-spec winner from a Rust winner in a tie — but the *deterministic-tie-break property* that the Kani harness explicitly verifies for the Rust side has no Quint analog. A future refactor that changes the Rust tie-break (e.g. to a fairness-weighted random scheme) would not be caught by Quint.
- **Why it succeeds**: Quint sets are not ordered; `fold` is permissive about iteration order. The Rust uses an ordered map and a stable sort. The Quint invariant is too weak to constrain this. The Kani harness `vickrey_tie_break_lowest_index` is the only check on tie-break determinism; the Quint side has no corresponding `inv_winner_deterministic_tiebreak` and the resolve action's `fold` is unable to express the constraint even if the invariant existed.
- **Suggested defense**: Replace the `fold` over `valid_bids` with an explicit "lex-smallest address among those at max_amount" pick. Add an invariant `inv_winner_lex_smallest_among_max: contract.phase == Complete and contract.winner != "" implies forall addr in valid_bids with decrypted.get(addr) == max_amount: contract.winner <= addr` (using a string-lex comparison helper). Note this requires modeling string comparison in Quint, similar to how ranked-choice introduced `lex_rank` for its 3-candidate universe.

## 8. [sealed-auction] Observer-flag reset semantics are misaligned with the Rust path — the contract never resets `bid_count` mid-round but the spec does on `start_auction`

- **Target spec**: `auction.qnt` lines 146-167, 453-458, 56-62
- **Category**: Observer/visibility model — partial coverage
- **Severity**: serious
- **Scenario**: The Quint `start_auction` action resets `observer'.current_round_has_revealed_ciphertexts: false` (line 161) and `contract'.bid_count: 0`. The Rust `exec_start_auction` (line 79-95) *deletes the SEALED_BIDS storage entries* in addition to resetting `bid_count = 0` and saving a fresh `AuctionRound`. The Quint analog `contract'.sealed_bids: Map()` (line 155) also resets the sealed_bids map. So the spec models the storage clearance. But `inv_ciphertexts_public` (lines 453-458) says `if bid_count > 0 then current_round_has_revealed_ciphertexts`. After `start_auction` clears both, the invariant is vacuous. Between bidding and resolve, the invariant fires and holds. But: the ledger note at line 92 says "observer-flag reset semantics may still be present depending on the agent's scope; verify in the diff." This is a flag for *under-coverage*: the observer model only tracks a binary "ciphertexts revealed yes/no" flag per round, but the actual chain state has a richer disclosure pattern — e.g. an observer can see WHICH addresses submitted bids, just not the amounts. The Quint observer model does not distinguish between "I see that addresses A, B, C submitted bids" and "I see that 3 bids were submitted" — both map to `bid_count > 0`. The privacy claim in the spec preamble (lines 8-12) is "Bid amounts are private during bidding (encrypted)"; the spec correctly captures that `can_see_bids` is always false. But the bidder-identity disclosure is partially captured by `contract.sealed_bids.keys()` being public and the absence of an invariant tying that key set to observer visibility. There is no invariant `inv_bidder_set_public` — so the privacy boundary between "amount" and "identity" is not made explicit in the verification surface.
- **Why it succeeds**: The observer model is intentionally coarse — `can_see_bids` (amount visibility) and `current_round_has_revealed_ciphertexts` (existence of submissions) — but does not model bidder-identity visibility. The Rust contract publishes addresses as `Map` keys, accessible via any RPC query. The privacy intent of a sealed-bid auction includes amount privacy but not identity privacy, so this is *not necessarily a bug* — but the spec is silent on which side of the privacy boundary it's enforcing. An external auditor reading the spec cannot tell whether bidder-identity disclosure is intentional or accidental.
- **Suggested defense**: Either (a) add an explicit `observer.visible_bidder_set: Set[Addr]` that mirrors `contract.sealed_bids.keys()`, and an invariant `inv_bidder_set_publishable: observer.visible_bidder_set == contract.sealed_bids.keys()` documenting that bidder identity is *intentionally* public, or (b) tighten the spec preamble at lines 8-12 to say "bid amounts are private; bidder identities are public" and skip the model.

## 9. [sealed-auction & ranked-choice] Admin authorization is unmodeled — both specs let any caller invoke admin-gated actions

- **Target specs**: `auction.qnt` lines 146-167 (`start_auction`), `ranked-choice.qnt` lines 263-285 (`create_election`, `open_voting`)
- **Category**: Coverage gap — composition with access control
- **Severity**: serious
- **Scenario**: `examples/sealed-auction/contracts/src/contract.rs:69-71` requires `info.sender == config.admin` to start a new auction. `examples/ranked-choice/contracts/src/contract.rs:62-65, 111-114` requires the same for `create_election` and `open_voting`. Neither Quint spec models a sender. The action `start_auction` is callable by anyone in the Quint state space. So any invariant that holds via "only the admin can advance the phase" is silently weakened to "anyone can advance the phase". For example, an attacker could in principle force a phase reset between bidding rounds, dropping bids. The Quint spec admits these traces; the Rust contract rejects them. The verification surface therefore over-approximates the reachable state space, producing invariants that hold under MORE conditions than the implementation actually permits — which is a soundness direction (over-approximation is OK for safety) — but it means the spec's invariants are weaker constraints than they could be.
- **Why it succeeds**: Quint has no first-class notion of "caller"; the spec's actions are top-level transitions with no implicit sender. Modeling admin authorization requires introducing a `caller: Addr` state variable or an explicit sender parameter, then guarding admin-only actions with `caller == ADMIN`. Neither spec does this.
- **Suggested defense**: Add a `caller: Addr` state variable to each spec and require `caller == ADMIN` on admin-gated actions. This will narrow the reachable state space and may *enable additional invariants* (e.g. "only the admin can transition from Complete back to Bidding"). The action would become `action start_auction(caller: Addr): bool = all { caller == ADMIN, ... }` with `nondet caller = oneOf(Set(ADMIN, SPONSOR_A, ...))` in `step`. The current omission is documented in neither spec.

## 10. [ranked-choice] Ballot universe slimming silently excludes the case of "ranked choice that gets filtered out by tally" — the Rust enclave's filter pass has no spec analog

- **Target spec**: `ranked-choice.qnt` lines 286-301, `enclave/src/request.rs:41-48`
- **Category**: Bounded-universe accuracy
- **Severity**: serious
- **Scenario**: The Rust `tally_election` decodes each ballot and *filters out candidates not in the registered set*: `ballot.ranked_choices.into_iter().filter(|c| candidates.contains(c)).collect()`. If the filtered list is empty, the ballot is dropped from the tally entirely (line 47-49: `if !valid.is_empty() { ballots.push(valid); }`). So a voter who ranks only non-registered candidates ("Eve" → "Frank") contributes nothing to any round — it's silently exhausted. The Quint `cast_ballot` action at line 297 *strictly* requires every choice to be a registered candidate (`b.indices().forall(i => contract.candidates.contains(b[i]))`). The Rust contract does NO such validation at submit time — it stores arbitrary ciphertext. Only the enclave filters at tally time. So the Quint spec models a *strictly stricter* submission gate than the Rust implements. Consequence: the Quint spec cannot exhibit traces where a voter casts a ballot that becomes fully exhausted via filtering. The bounded universe BALLOT_UNIVERSE only contains ballots over the registered ALICE/BOB/CAROL — but the Quint spec is correct *only* for the ALL_CANDIDATES create_election variant. The two-candidate variants `Set(ALICE, BOB)` (line 329) and `Set(ALICE, CAROL)` (line 330) ARE present and exercise the "ranked choice not in registered set" case for ballots like `[CAROL, ALICE, BOB]` against `Set(ALICE, BOB)` — but the Quint `cast_ballot` REJECTS such ballots at submit time, whereas the Rust would store them and then filter at tally. Concrete trace: `create_election(Set(ALICE, BOB))` → `open_voting` → `cast_ballot(v1, [CAROL, ALICE])`. In Quint, this is rejected at submit. In the Rust contract, this is accepted (the contract has no candidate validation in `exec_cast_ballot`), stored on-chain, then at tally the enclave filters CAROL out and treats the ballot as `[ALICE]`. The Quint spec cannot reach the post-tally state for this trace; the Rust can.
- **Why it succeeds**: The contract-side validation gap (`exec_cast_ballot` at `contract.rs:128-155` has no candidate-set check) means the chain accepts arbitrary ballot contents, and the enclave is the only filter. The Quint spec moves the validation upstream into `cast_ballot`, which is a *tighter* model. Tighter models miss bugs where the enclave's filter doesn't match what the chain has stored — e.g. an enclave version skew where the registered candidate set differs between contract and enclave. The Apalache BMC will not exercise the "voter cast a ballot with all non-registered choices" trace because Quint's `cast_ballot` rejects it.
- **Suggested defense**: Either (a) relax `cast_ballot` to drop the `b.indices().forall(...)` constraint and instead model the filter in `tally`, OR (b) document explicitly that the spec assumes the enclave's filter and the contract's submission gate are aligned (which they currently are not — the contract has no gate). Option (a) requires modeling the enclave's filtering behavior; option (b) is honest about the simplification but flags a real gap between intent and implementation.

## 11. [sealed-auction] Per-sponsor pre-bound `nondet` amounts limit `resolve` to a 3-bidder universe smaller than the bidder space

- **Target spec**: `auction.qnt` lines 298-333
- **Category**: Bounded-universe accuracy / nondet limitation
- **Severity**: advisory
- **Scenario**: The `step` action pre-binds three `nondet` amounts (`amount_a`, `amount_b`, `amount_c`) — one per candidate sponsor (A, B, C) — and then constructs `decrypted_bids` by mapping each sealed-bids key to its pre-bound amount. The docstring at lines 304-311 acknowledges this is a workaround for Quint's missing "nondet per element" capability. Consequence: in any single `step` transition that calls `resolve`, the decrypted amounts are *fixed* by the three nondet bindings — but those three bindings are chosen at the *step* level, not at the *resolve action* level. If `step` is invoked multiple times before `resolve` succeeds (e.g. several `tick`s followed by a `resolve`), the resolve uses the latest step's nondet bindings, not the bindings at any prior step. This is sound but limits trace diversity: the spec cannot exhibit a trace where one sponsor's bid amount is `X` from the enclave's perspective at one moment and `Y` at another — which is *exactly the kind of consistency check* needed to catch enclave-vs-chain decryption drift (e.g. if the enclave decrypts the same ciphertext twice and gets different plaintexts due to a key-rotation bug). The pre-binding pattern is fine for verifying "the resolve action correctly computes Vickrey from a fixed decryption", but cannot verify "the resolve action's decryption is deterministic across multiple invocations".
- **Why it succeeds**: Quint 0.32's nondet introduction is `step`-scoped. The pre-binding workaround is the only way to express per-key randomness today. The spec acknowledges this. The limitation is documented but not flagged as a coverage limit on the verification claims.
- **Suggested defense**: Document the limitation in the spec preamble or in the verification status table: "this spec verifies single-shot Vickrey correctness against any consistent decryption snapshot but does not verify decryption-result invariance across re-invocations." If/when Quint adds per-element nondet, lift the pre-binding.

## 12. [sealed-auction] `start_auction` does not require a session to have been established — but the `session_active` invariant gates only the *during* phases

- **Target spec**: `auction.qnt` lines 146-167, 444-451
- **Category**: Edge case / refactor hazard
- **Severity**: advisory
- **Scenario**: `inv_session_required` at lines 444-451 says: if phase is Bidding, Resolving, or Complete, then `contract.session_active` must hold. But `start_auction` (line 148) requires `contract.session_active` as a precondition, AND `init` (line 123) sets `session_active: true`, AND no action ever sets `session_active' = false`. So `session_active` is always true in every reachable state. The invariant is vacuous — it never *could* fail. The Rust intent is that the Quartz handshake (modeled at the `quartz_contract_core` layer, not here) establishes the session, and that the contract refuses to operate without it. The Quint spec captures this via the precondition on `start_auction`, which is fine — but the invariant adds nothing because no spec action invalidates the session. If the spec is later extended with a `close_session` or `expire_session` action (a feature implied by the larger Quartz design — see `crates/contracts/core/src/state.rs` Session lifecycle), the invariant would fire — but it would also fire trivially because no current action *enters* a non-session-active state. The invariant is dormant: structurally present but exercised by no path.
- **Why it succeeds**: The session-lifecycle is modeled at a higher abstraction layer in `specs/handshake.qnt` and is not under the auction's control. The auction spec correctly defers to that layer by treating `session_active` as a precondition. But the invariant `inv_session_required` is a sanity check that has no corresponding falsifying action in the spec, making it a "dormant" invariant in the round-1 S1 sense.
- **Suggested defense**: Either (a) delete `inv_session_required` (it's redundant given `session_active` is constant-true), or (b) add a `lose_session: contract' = { ...contract, session_active: false }` action with no other effects and re-run BMC to verify the invariant prevents auction operation under that condition. Option (b) earns the invariant its keep; option (a) trims the dead weight.
