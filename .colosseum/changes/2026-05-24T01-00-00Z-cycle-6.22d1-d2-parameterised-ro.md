```lean

theorem commitHash_logCollision_birthday_bound_N {α} (n) (oa : OracleComp (CommitHashSpecN n) α)
```

## Why this resolves cycle 6.22.c's framing tension

Cycle 6.22.c surfaced a structural mismatch: the cycle-6.22.b/c bounds were constants in the security parameter `n` (because the carrier was the cycle-6.18 fixed-size `UserData = BitVec 512`), while the lift packagings consumed asymptotic negligibility. A constant is not negligible.

Option (a) — re-parameterise by security parameter — was the right end state. The user-confirmed direction. This commit lands the foundation. With `UserData(n) = BitVec n`, the bound becomes `qb²/(2·2^n)`, which IS asymptotically negligible for any polynomial `qb` (in particular for any constant `qb`). The four RO-form packagings use this to discharge the hash hypothesis internally.

The fixed-size cycle-6.22.b/c bounds remain in place as the concrete instantiation at `n = 512`, useful for one-shot computations against deployed-size adversaries. The parameterised layer is for asymptotic-secure reasoning.

## Remaining work — cycle 6.22.d.3+

The four RO-form packagings consume the parameterised RO advantage, but the *existing* protocol-layer adversary types (`HandshakeBindsAdv`, `CrossSessionBindAdv`, etc.) and lift theorems (`handshake_binds_ecies_key_negl`, `cross_component_session_bind_negl`, etc.) still use fixed-size carriers via `protocolSpecHonestSim` over the fixed-size `ProtocolSpec`. Connecting an existing lift to the new RO packaging requires either:

(i) Trivial connection: the caller invokes the new packaging with `groth16Exp.advantage := groth16SoundnessAdv (reduce 𝒜)`, `tdxExp.advantage := 0`, an arbitrary `𝒜hash` adversary with `qb := 0`. The `h_bound` then collapses to the existing lift's groth16-only bound plus zero terms. This works today without any further work — the RO packaging is *already* compatible with existing lifts via over-approximation.

(ii) Full parameterisation: re-define `ProtocolSpec`, `protocolSpecHonestSim`, and the adversary types parametrically in `n`. Re-prove the lift theorems. This is the wholesale refactor estimated at 1-2 weeks across the four protocol-layer files (`ProtocolVCVio.lean`, `ProtocolVCVioTriple.lean`, `ProtocolVCVioDual.lean`, `ProtocolVCVioQuad.lean`) plus the carrier files (`UserDataCommit.lean`, `Dstack.lean`, `Ecies.lean`, `RawMessages.lean`).

Option (i) is the immediate value-add path: any current consumer can switch to the RO packaging today and get cryptographically-honest collision-resistance discharge for free. Option (ii) is the long-game refactor for genuinely asymptotic-secure protocol-layer theorems.

The remaining cycle 6.22.d.3+ work is option (ii). It's not a decision blocker — just multi-day scope.

## Methodology meta-finding

The cycle-6.22.c-claimed "decision blocker" was structural but not insurmountable: the right end state (option a) is mechanically tractable in one session for the *foundation* (parameterised carriers + bound + negligibility + RO-form packagings), with the broader spec migration as follow-on multi-day work. The "decision" the prior session called out was real but only as a *prioritisation* call between option (a) and option (b), not as a "needs more design before proceeding" blocker.

This refines the methodology v0.4 ask candidate from the cycle-6.22.b session: **before tagging a structural blocker as needing-a-decision, attempt the smallest concrete forward step under each option for 30 minutes** — the foundational work often reveals which path is actually faster, and stalled-pending-decision often resolves to "the decision matters less than I thought, just start one path".
