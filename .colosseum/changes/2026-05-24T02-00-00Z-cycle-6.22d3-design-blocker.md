# Cycle 6.22.d.3 — wholesale spec parameterisation blocked on staging-design decision

- Date: 2026-05-24
- Scope: no code changes; documentation of design blocker for the remaining cycle 6.22.d work

## Context

Cycles 6.22.d.1, 6.22.d.2, and 6.22.d.2.5 landed the foundation of option (a) for closing the cycle-6.22.c framing tension:

* Parameterised RO model and asymptotic negligibility (cycle 6.22.d.1).
* Four RO-form packagings that discharge collision-resistance internally (cycle 6.22.d.2).
* Four connection theorems wiring existing lifts through the new RO packagings (cycle 6.22.d.2.5).

The remaining work — true wholesale parameterisation of the protocol-layer adversary types, advantage definitions, lift statements, and lift proof bodies — is **multi-day in scope and gated on a staging-design decision** before execution can sensibly start.

## Why it can't just be done incrementally

`UserData` appears 119+ times across 13 files in `Specs/Quartz/*`. Mechanically replacing `UserData` with `UserData_N n` requires answering three design questions, each load-bearing:

### (1) Keep or replace the deployed-size carrier?

The current `abbrev UserData : Type := BitVec 512` (in `Specs/Quartz/Attestation/Dstack.lean`) corresponds to the production dstack quote layout. Two options:

* **(1a)** Replace in place: `abbrev UserData (n : ℕ) : Type := BitVec n`. All deployed-size statements gain a parameter. The concrete instantiation `n = 512` becomes a corollary.
* **(1b)** Add a parallel `abbrev UserData_N (n : ℕ) : Type := BitVec n` alongside the fixed-size `UserData`. Existing theorems unchanged; new theorems get a new `_N` suffix. Two parallel ecosystems.

Tradeoff: (1a) is cleaner but breaks every existing statement; (1b) is safer but doubles the surface area.

### (2) Parameterise the bundle axiom or family-of-axioms?

The cycle-6.18-refined carrier axiom `commitHashE : UserDataCommit ↪ UserData` becomes:

* **(2a)** Under (1a): `axiom commitHashE (n : ℕ) : UserDataCommit ↪ UserData n` — a single parameterised axiom.
* **(2b)** Under (1a) or (1b): keep `commitHashE : UserDataCommit ↪ UserData` (fixed size) and introduce a parallel `axiom commitHashE_N (n : ℕ) : UserDataCommit ↪ UserData_N n`.

(2a) is honest about scaling. (2b) preserves the existing axiom for legacy consumers.

Note: this axiom is *spec-impossible* by pigeonhole (cycle-6.22 closes it via the RO model). Adding a parameterised version replicates the dishonesty; the RO-form packagings (cycle 6.22.d.1/.2) are the right path forward. So the parameterised axiom is really only there as a parametric *trust boundary* for any consumer not yet on the RO path.

### (3) Migrate the protocol-layer adversary types in place or in parallel?

The cycle-6.13 adversary types `HandshakeBindsAdv := ℕ → OracleComp ProtocolSpec ...` use the fixed-size `ProtocolSpec`. Options:

* **(3a)** Replace: `HandshakeBindsAdv (n : ℕ) := (m : ℕ) → OracleComp (ProtocolSpec_N n) ...` — adversary types double-indexed (security parameter + invocation count).
* **(3b)** Add parallel `HandshakeBindsAdv_N` alongside. Existing lift theorems unchanged; new parameterised lift theorems prove the parameterised conclusion.

(3a) is the right end state for asymptotic security. (3b) lets the migration proceed lift-by-lift over weeks.

## The decision blocker

The three choices interact. Some non-trivial combinations are degenerate (e.g., (1b) + (2a) makes no sense), others are sensible.

A maintainer needs to choose:

* **Aggressive replacement (1a/2a/3a)**: every Specs/Quartz/* theorem statement changes. Single big-bang commit (or staged across two or three commits with broken intermediate builds). ~1 week focused work, high risk of subtle proof regressions.
* **Conservative parallel (1b/2b/3b)**: existing tree unchanged, parallel parameterised tree grows alongside. Every consumer that wants asymptotic security imports the parameterised tree explicitly. ~2-3 weeks because everything is essentially duplicated, low risk. Long-term: technical debt as the two trees diverge.
* **Hybrid (1a/2a/3b)**: carrier and axiom replaced (1a/2a), adversary types parallel (3b). New parameterised lift theorems prove parameterised conclusions; old fixed-size lifts still typecheck because the parametric axiom specialises at `n = 512`. Probably the right shape if option (a) is the long-term direction. ~1-1.5 weeks.

This isn't a "needs more cryptographic understanding" blocker — it's a staging / coordination call that affects every consumer of `Specs/Quartz/*` and should be made by the maintainer, not the verification agent.

## Methodology meta-finding

This is the *second* time in the cycle-6.22 sequence that what looked like a structural blocker turned out to be a staging-design call. The previous instance was cycle-6.22.c's "asymptotic-framing decision" which the agent labelled as needing-a-decision but which the user resolved in one word ("a") because the cryptographic content was already clear. The current cycle-6.22.d.3 blocker is similar: the substantive work is mechanically tractable; the choice is *how to stage* the breaking change.

Refined v0.4 methodology ask candidate (consolidating both instances): **distinguish "structural blocker" from "staging-design blocker" in change records.** A structural blocker means a fact about the verification or cryptographic surface that prevents the proof from going through. A staging-design blocker means the proof can go through but the choice of how to integrate breaking changes affects every consumer. The two need very different treatment — the first requires research, the second requires the maintainer's input on coordination cost vs end-state cleanliness.
