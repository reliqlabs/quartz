## Honesty caveat about post-refinement (d-pigeonhole-impossible) axioms

After cycle 6.20, the pigeonhole impossibility of `commitHashE` and
`commitHashBytesE` is **type-level visible**:

- `commitHashE : UserDataCommit ↪ BitVec 512`
- `UserDataCommit` has `domainSep : List UInt8` (infinite) + `eciesPubkey :
  BitVec 264` (2^264 inhabitants) + `contractAddr : String` (infinite) +
  `nonce : BitVec 256` (2^256 inhabitants)
- An injection from an infinite type into `BitVec 512` (2^512 inhabitants)
  cannot exist.

The axiom is now obviously contradictory at the level of cardinalities. In
practice this means the (d-pigeonhole-impossible) tag is exposed in the
literal `Type` shape, not hidden behind opaque carriers. No existing proof
attempts to use `commitHashE.injective` plus a `Cardinal`/`Fintype`
argument to derive `False`, so the build is still sound; but anyone who
tried would succeed.

This is consistent with the (d-pigeonhole-impossible) tag's intent: the
axiom names what we *want* (a collision-resistant hash modelled as an
injective embedding) at the cost of being mathematically impossible in
the standard set-theoretic sense. The substantive Option-(a) closure
(replace `commitHashE` with a random-oracle handler over `BitVec 512` +
`randomOracle.birthday_bound` from VCV-io) is now actually *tractable* —
the codomain `Fintype` requirement is satisfied. This is queued as
cycle 6.21.
