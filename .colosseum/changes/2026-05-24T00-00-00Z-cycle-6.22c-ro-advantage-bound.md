## What landed

Two new types, two advantage definitions, two bound theorems:

```lean
def CommitHashCollisionAdvRO : Type :=
  ℕ → OracleComp CommitHashSpec Unit

noncomputable def commitHashCollisionAdvRO
    (𝒜 : CommitHashCollisionAdvRO) (n : ℕ) : ℝ≥0∞ :=
  Pr[fun z => LogHasCollision z.2 |

theorem commitHashCollisionAdvRO_le_birthday_bound
    (𝒜 : CommitHashCollisionAdvRO) (qb : ℕ)
```

## Why use the log-collision shape rather than the win-pred shape

The natural "explicit win" event for a collision-finder is:

```
adversary outputs (uc₁, uc₂); verifier queries oracle(uc₁), oracle(uc₂);
win iff uc₁ ≠ uc₂ ∧ oracle(uc₁) = oracle(uc₂)
```

Under VCV-io's `evalDist` semantics (no caching; each query is an independent uniform), the verifier's two queries return independent uniforms. For distinct inputs, `Pr[h₁ = h₂] = 1/2^512` regardless of the adversary's query strategy. The bound is tighter than the birthday bound (`1/2^512` vs `q²/(2·2^512)`).

The log-collision shape proven here bounds a strictly stronger event: "any two distinct queries in the trace returned equal values" — which subsumes both the verifier's two queries colliding AND the adversary's own queries colliding among themselves. The birthday bound is the natural bound for this event under independent-uniform semantics.

For the downstream lift consumer, the log-collision shape is sufficient because: if the adversary asserts a collision (in any reasonable game), it must have witnessed it via oracle queries, which appear in the log.

## What remains as cycle 6.22.d (blocked on a decision)

The cycle-6.4–6.11 over-bundling finding established that the four downstream lifts (`handshake_binds_ecies_key_negl`, `session_confidentiality_negl`, `session_confidentiality_via_extractor_negl`, `cross_component_session_bind_negl`) don't actually consume the `CommitHashCollisionAdv` hypothesis in their proof bodies — only the `*_secure_of_*_bundle_secure` packaging wrappers do, where it appears as a parametric negligibility input.

The packaging wrappers take `h_hash_secure : hashGame.secureAgainst IsPPT` and conclude `bindsGame.secureAgainst IsPPT` via union bound + negligibility-closure. The migration to RO-shape would instantiate `hashGame.advantage := commitHashCollisionAdvRO` and discharge `h_hash_secure` via the cycle-6.22.c bound.

**The blocker**: the bound `commitHashCollisionAdvRO 𝒜 n ≤ qb²/(2·2^512)` is a *constant* in the security parameter `n`. The asymptotic-security framework requires the advantage to vanish as `n → ∞`. With fixed-size hash (`UserData = BitVec 512`), the bound does not vanish; `qb²/(2·2^512)` for any polynomial `qb(n)` is asymptotically `polynomial/constant = polynomial`, not negligible.

Three remediation options, each requiring a design decision:

(a) **Re-parameterize the spec by security parameter**: `UserData(n) := BitVec (security_param n)` and similarly for the hash carriers. This makes the bound `qb(n)²/(2·2^(security_param n))`, which IS negligible for any polynomial `qb(n)` and security_param growing super-logarithmically. Major refactor: every carrier-using theorem in `Specs/Quartz/*` would need to be parameterized. Estimated effort: 1-2 weeks.

(b) **Re-frame the packagings to expose concrete bounds**: replace `*_secure_of_*_bundle_secure` with `*_advantage_le_of_*_bundle_advantage_le`, where the conclusion is a *concrete* pointwise bound on `bindsFailExp.advantage n` instead of `bindsFailExp.secure`. The hash component contributes a constant `qb²/(2·2^512)` summand directly via the cycle-6.22.c bound; the Groth16/TDX components contribute negligible summands. The conclusion is honestly mixed: "Groth16 + TDX is negligible; hash adds a constant 2^-O(1) bound". Negligibility framing is dropped for the hash term. Estimated effort: 2-3 days. Honest about fixed-size hash.

(c) **Add a "hash advantage is negligible" axiom**: introduce `axiom hashAdvIsNegligible : negligible commitHashCollisionAdvRO`. This is mathematically false (the bound is a positive constant, not vanishing), but it preserves the existing packaging shape. Not recommended — moves the dishonesty from "axiom commitHashE is impossible" to a new fake axiom of the same flavor.

The right answer is (a) — it's the only one that admits a genuinely asymptotic-secure conclusion. (b) is the honest interim shape if (a) is too expensive right now. (c) is a regression.

This is a design decision because each option changes the load-bearing shape of every protocol-layer theorem statement. The cryptographic content (the birthday bound) is now proven; the wiring decision is structural.

## Methodology meta-finding

The cycle-6.22 sequence exposed a structural mismatch the prior methodology didn't flag: spec-level use of fixed-size cryptographic carriers (`BitVec 512`, etc.) combined with asymptotic-security framing in the lift packagings. The two are incompatible — either the spec parameterizes by security parameter, or the packagings expose concrete bounds. The original Round A attack #8 was about def-tying the advantage shape; cycle 6.22 substantively closes that but reveals the deeper framing tension.

Add to colosseum methodology v0.4 ask candidates: **for any cryptographic spec using fixed-size carriers, the lift packagings must expose concrete advantage bounds rather than asymptotic-negligibility conclusions, unless the carriers are explicitly parameterized by security parameter.** A pre-flight check during spec authoring would have flagged the BitVec 512 / negligibility mismatch at carrier-definition time.
