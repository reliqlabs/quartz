## What this cycle changes

Replaces `axiom Nonce : Type` with
`abbrev Nonce : Type := BitVec 256`.

The choice of `BitVec 256`:

- Mirrors the production Rust representation `[u8; 32]` (32 bytes = 256 bits).
- Automatic `Fintype` instance (`BitVec n` has size `2^n`).
- Automatic `DecidableEq`, `Inhabited`, `Repr` instances.
- `abbrev` (rather than `def`) so the refinement is reducible, preserving all
  pre-cycle-6.16 definitional equalities downstream.

## Downstream impact

`Nonce` had limited usage — only 4 sites:

1. The carrier declaration itself (`UserDataCommit.lean:107`).
2. `UserDataCommit.nonce : Nonce` field.
3. `RawSessionCreate.nonce : Nonce` field.
4. `RawSessionSetPubKey.nonce : Nonce` field.

`abbrev` reducibility ensures all four downstream sites are unaffected;
the structures `UserDataCommit`, `RawSessionCreate`, `RawSessionSetPubKey`
now have a concrete `BitVec 256`-typed `nonce` field, but every theorem
treating these structures as opaque records is unchanged.

## Why `Nonce` first

`Nonce` was the smallest atomic carrier in the queue:

- Only 4 usage sites (vs e.g. `Addr` with more, `PubKey` cascading
  through ECIES, `UserData` cascading through every lift's win
  predicate).
- Production representation `[u8; 32]` maps cleanly to `BitVec 256`.
- Refinement does not interact with `commitHashE` / `commitHashBytesE`
  (the impossible pigeonhole axioms) — those remain in place pending
  carrier refinement on `UserData`, which is the next non-trivial
  cascade.

## What this does NOT unblock

The cycle is intentionally minimal. It does *not*:

- Demote `rawDomainSep`, `rawBoundContract`, or `rawPlaceholderPubKey`
  to `def`s — those require refinement of `DomainSep`, `Addr`, `PubKey`
  respectively, which is queued.
- Provide a `Fintype UserDataCommit` instance — that requires *all*
  four `UserDataCommit` field types to refine (`DomainSep`, `PubKey`,
  `Addr`, `Nonce`). Only `Nonce` is concrete now.
- Discharge the `commitHashE` pigeonhole-impossible axiom — that
  requires `Fintype UserData` plus a random-oracle reduction.

## Next carrier refinement candidates

In rough order of tractability:

1. `MrEnclave` → `BitVec 384` or `Vector UInt8 48` (Intel TDX
   MRTD/RTMR is a 48-byte SHA-384 digest; 4 lift carriers + classical
   theorems).
2. `UserData` → `BitVec 512` or `Vector UInt8 64` (DCAP `report_data`
   is 64 bytes; 8-of-8 lift carrier; cascading impact on
   `commitHashE` and `commitHashBytesE`'s codomain).
3. `Plaintext` → `ByteString` or `List UInt8` (application-level,
   variable-length; 4 lift carriers via ECIES).
4. `DomainSep` → `ByteString` (variable-length ASCII tag; would also
   demote `rawDomainSep`).
5. `Addr` → `String` or a structured bech32 type (would also demote
   `rawBoundContract`).

`UserData` refinement (item 2) is the highest-leverage move: it
provides the codomain `Fintype` needed for the `commitHashE` /
`commitHashBytesE` random-oracle discharge that Round A attack #8
substantively requires.
