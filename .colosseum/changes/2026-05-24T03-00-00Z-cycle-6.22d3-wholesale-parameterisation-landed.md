### `IsPPT_proper` generalisation

`IsPPT_proper` previously took `T : Type` for adversary result type. Several adversaries (notably `HandshakeSoundAdv`) now have result types `HandshakeCheck n` that depend on `n`. Generalised to `T : ℕ → Type` so adversaries with sec-param-dependent output types fit the predicate. `IsPPT_proper_of_bind_pure_comp` correspondingly takes `S, T : ℕ → Type` and a per-`n` reduction function `f : (n : ℕ) → S n → T n`. The four reduction-preservation theorems (`reduce_handshake_to_groth_preserves_IsPPT_proper`, `reduce_binds_to_groth_preserves_IsPPT_proper`, `reduce_transfers_to_groth_preserves_IsPPT_proper`, `reduce_auctionDeterm_to_groth_preserves_IsPPT_proper`, `reduce_crossSessionBind_to_groth_preserves_IsPPT_proper`) supply `T` explicitly (`T := fun n => HandshakeCheck n × ...`).

## Resolution of the cycle 6.22.c framing tension

* Before: `qb²/(2·2^512)` was a constant in `n`; the lift packagings' asymptotic-negligibility hypothesis was incompatible.
* After: `qb²/(2·2^n)` is super-polynomially decaying in `n`. `commitHashCollisionAdvRO_negligible_of_constant_qb` proves negligibility from the birthday bound. The four RO-form packagings consume the proven negligibility internally — no hash collision-resistance hypothesis required from the caller.

## Methodology meta-finding

The maintainer's choice was "aggressive replacement with test-as-you-go" rather than the parallel-tree approach. In practice this meant:

* One major foundational change per file/section.
* Immediate per-file `lake env lean` after each edit.
* Full `lake build` after each file group to surface cascading errors.
* No intermediate broken commits; the entire wholesale refactor landed as a single coherent set of changes once the build returned green.

The estimate said ~1 week. The actual landed in one focused session because the per-file changes were mechanical once the design pattern (security parameter as outer `Nat` argument threaded through everything) was established. The hardest single sub-piece was generalising `IsPPT_proper` from `T : Type` to `T : ℕ → Type` to accommodate `HandshakeSoundAdv`'s dependent return type — Lean's higher-order unification doesn't auto-infer the `T` from `HandshakeCheck`, so reduction-preservation theorems supply `T` explicitly.

Refined v0.4 methodology ask: when a parameterisation refactor crosses a typeclass like `IsPPT_proper`, audit whether the typeclass's adversary-result type parameter should become security-parameter-dependent (`Type` → `ℕ → Type`) before starting the file-by-file migration. The check is mechanical (does any adversary's output type depend on the security parameter?) and surfaces the dependency early.
